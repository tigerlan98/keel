# 02 技术选型与整体架构

> 状态：v0.3（评审确认定稿）
> 更新：2026-11-12
> 关联：`01-需求与功能模块梳理.md`、`03-数据库设计.md`、`04-API接口设计.md`、`05-实施计划与工程规范.md`、`06-设计方案评审结果.md`、`../rules/database-rules.md`、`../rules/api-rules.md`

## 1. 架构目标与原则

1. **简单优先**：不为假设中的未来需求提前设计。
2. **模块优先**：模块边界比形式化分层更重要。
3. **实用 DDD**：按业务复杂度决定抽象深度，简单 CRUD 不强行建领域层。
4. **依赖清晰**：模块依赖与分层边界用 ArchUnit 固化。
5. **适度扩展**：新增业务模块只需增加依赖与包结构。
6. **技术克制**：不引入微服务、CQRS、事件总线、分布式事务。
7. **易于维护**：结构直观，适合个人、团队与 AI Agent。

整体形态：**单体多模块（Modular Monolith）**，单应用部署，前后端分离。

## 3. 模块结构

### 3.1 模块图

```
keel（根 pom）
├── keel-bootstrap              启动、装配、全局配置、ArchUnit 测试
├── keel-iam                    用户、登录会话、角色、资源、菜单、授权
├── keel-system                 系统参数
├── keel-audit                  操作日志、登录日志
├── keel-common-core            返回、错误码、异常、跨模块契约
├── keel-common-web             全局异常、校验、Web 约定
├── keel-common-security        Security、token、当前用户、鉴权
├── keel-common-persistence     持久层配置、基础实体、通用拦截器
└── keel-common-test            测试基座（test scope）
```

### 3.2 依赖矩阵

| 模块 | 编译依赖 |
|---|---|
| `keel-bootstrap` | 全部业务模块与 common 模块；test 依赖 `common-test` |
| `keel-iam` / `keel-system` / `keel-audit` | `common-core`、`common-web`、`common-security`、`common-persistence` |
| `common-web` | `common-core` |
| `common-security` | `common-core`、`common-web` |
| `common-persistence` | `common-core` |
| `common-test` | 测试库 + `common-core`（可选），仅 test scope |

业务模块之间零直接依赖；跨模块协作只通过 common 中的端口与事件契约。

### 3.3 包结构

以 `keel-iam` 为例：

```
io.github.keel.iam
├── api                        对外接口与 DTO
├── interfaces/admin           Controller
├── application
│   ├── identity               用户、密码、资料
│   ├── authentication         登录、登出、会话
│   └── authorization          角色、资源、菜单、授权
├── domain
│   ├── user
│   ├── role
│   └── resource
└── infrastructure/persistence  Mapper、PO、XML
```

common 包：

```
io.github.keel.common.core          Result、ErrorCode、异常、跨模块契约
io.github.keel.common.web           全局异常处理、参数校验、Web 约定
io.github.keel.common.security      Security 配置、token、当前用户
io.github.keel.common.persistence   持久层配置、基础实体、通用拦截器
```

### 3.4 DDD Lite 分层

| 层 | 职责 |
|---|---|
| `interfaces` | 参数接收、校验、调用应用服务、返回 VO |
| `application` | 用例编排、事务边界、DTO 转换 |
| `domain` | 复杂业务规则、领域服务、聚合；简单 CRUD 可省略 |
| `infrastructure` | Mapper、PO、外部适配、Redis 访问 |

对象模型：

| 对象 | 位置 | 说明 |
|---|---|---|
| `XxxPO` | `infrastructure/persistence` | MyBatis-Plus 映射对象，可写，Lombok |
| `XxxDTO` | `application` / `api` | 应用层入参出参，record |
| `XxxVO` | `interfaces` | 接口响应，record |
| 领域实体 | `domain` | 仅复杂聚合使用 |

### 3.5 跨模块契约

| 契约 | 所在模块 | 实现方 | 使用方 |
|---|---|---|---|
| `CurrentUserProvider` | `common-core` | `common-security` | `common-persistence`、业务模块 |
| `PermissionProvider` | `common-security` | `keel-iam` | Spring Security 鉴权 |
| `ConfigProvider` | `common-core` | `keel-system` | 需要动态参数的模块 |
| `LoginLogEvent` / `OperationLogEvent` / `@OperationLog` | `common-core` | `keel-audit` 消费 | `keel-iam`、`keel-system` |
| `DataScopeProvider`（仅预留） | `common-persistence` | `keel-iam`（未来） | 数据权限拦截器（未来） |

事件消费语义：

- `LoginLogEvent` 同步消费，在登录成功、登录失败、登出的同一请求内落库。
- `OperationLogEvent` 在事务提交后异步消费；事务回滚时不产生操作日志。
- 审计实现位于 `keel-audit`，业务模块只依赖 `common-core` 中的事件与注解契约。

### 3.6 ArchUnit 规则

1. `common-*` 不得依赖 `iam`、`system`、`audit`。
2. 业务模块之间禁止直接依赖。
3. `..interfaces..` 不得被其他模块或本模块下层依赖。
4. `..domain..` 不得依赖 `..infrastructure..` 与 `..interfaces..`。
5. `..api..` 不得依赖 Web 与持久化框架类型。
6. `..application..` 不得依赖 Web 类型。
7. `bootstrap` 不得包含业务逻辑。
8. `iam` 内部子域不得访问彼此的 `infrastructure` 与 `interfaces`。
9. `common-core` 不得依赖 Spring Web、Security、MyBatis（POM 已保证，ArchUnit 二次防线）。

ArchUnit 测试放在 `keel-bootstrap` 的测试源码中，CI 失败即阻断。

### 3.7 bootstrap 的职责

- 启动类、全局配置、profile、日志配置。
- 跨模块装配与 Bean 注册。
- 可执行 jar 入口。
- 不包含 Controller、Application Service、Domain、Mapper、业务规则。
- 验收标准：新增业务模块时，`bootstrap` 只增加一行 Maven 依赖。

## 4. 认证与授权架构

### 4.1 Opaque Token

| 项目 | 设计 |
|---|---|
| 生成 | 32 字节随机数，Base64URL |
| 存储 | Redis 只存 SHA-256 哈希 |
| 元数据 | `userId`、`loginType`、`device`、`issuedAt`、`lastAccessAt`、`absoluteExpireAt`、`ip`、`userAgent` |
| 空闲过期 | Redis TTL，请求时续期 |
| 绝对过期 | 请求时校验 `absoluteExpireAt` |
| 索引 | `auth:user:{loginType}:{userId}` Hash，字段 `device → tokenHash` |
| 吊销 | 删除 token 键与索引字段；踢全部端时删除该用户在 `ADMIN`、`APP`、`MINI` 各索引键中的字段 |
| Refresh Token | 不做；滑动 + 绝对过期，过期后重新登录 |

### 4.2 Web / App 双模式

| 客户端 | 传输 | CSRF |
|---|---|---|
| Admin 浏览器 | `HttpOnly` / `Secure` / `SameSite=Lax` Cookie | 启用 |
| App / 小程序 | `Authorization: Bearer <token>` | 跳过 |

- 登录接口接收 `device`：`WEB` 设置 Cookie；`APP` / `MINI` 在响应体返回 token。
- 服务端由 `device` 派生登录日志的 `loginType`：`WEB → ADMIN`，`APP → APP`，`MINI → MINI`。
- `TokenAuthenticationFilter` 解析顺序：`Authorization` 头 → Cookie。
- CSRF 使用 `CookieCsrfTokenRepository.withHttpOnlyFalse()`，前端读 `XSRF-TOKEN` 并回传 `X-XSRF-TOKEN`；Bearer 请求通过 `RequestMatcher` 跳过。
- 登出删除 Redis token、清理索引、清除 Cookie。

### 4.3 会话策略

- 按设备单会话：同设备新登录踢旧 token，不同设备可同时在线。
- Web 空闲 30 分钟、绝对 12 小时。
- App 空闲 7 天、绝对 30 天。
- 提供按用户 / 设备强制下线接口，不做在线会话页面。

### 4.4 鉴权

- Security 配置为 STATELESS，关闭表单登录与 `HttpBasic`。
- 接口使用 `@PreAuthorize("@perm.has('iam:user:create')")`。
- `PermissionChecker` 先判断 `SUPER_ADMIN`，再比对权限码。
- 401 未认证，403 无权限；401 清理前端登录态并跳转，403 只提示。

### 4.5 权限模型

- 统一资源树：目录、菜单、按钮、接口共用权限码。
- 角色与资源多对多；用户与角色多对多；角色扁平。
- `SUPER_ADMIN` 内置角色，不可删除、不可改 code、不可禁用，持有者绕过校验。
- 权限缓存键 `iam:perm:{userId}`，TTL 30 分钟；角色、资源、用户-角色、用户状态变化时失效。
- `/me` 返回用户、`superAdmin`、权限码、菜单树。

### 4.6 生命周期联动

| 事件 | 动作 |
|---|---|
| 用户禁用 | 删除该用户全部 token，清除权限缓存 |
| 密码重置 | 标记首次改密，删除全部 token |
| 角色授权变更 | 删除受影响用户的权限缓存 |
| 角色状态变更（启用或停用） | 删除受影响用户的权限缓存 |
| 资源状态变更（启用或停用） | 停用前校验无启用子资源；删除受影响用户的权限缓存 |
| 管理员强制下线 | 删除目标 token 与索引字段 |

## 5. 数据与持久化架构

- 单库单 schema，表名按模块前缀：`iam_`、`sys_`、`aud_`。
- MyBatis-Plus 只使用 `BaseMapper` 与显式 SQL；禁止 `IService` / `ServiceImpl`。
- 复杂查询写 XML，SQL 只出现在 `infrastructure/persistence`。
- Flyway 按模块归属脚本，版本段：`iam` 1000–1999、`system` 2000–2999、`audit` 3000–3999；跨模块种子统一放 `bootstrap` 的 9000–9999。
- 主键自增 `BIGINT`；审计字段 `created_at/by`、`updated_at/by`；`version` 仅按需。
- 时区统一 `Asia/Shanghai` 本地时间（规范推荐 UTC，本项目按单时区部署明确记录为例外）；JVM、MySQL 会话、JDBC 连接三处一致。
- 不做全局逻辑删除：用户/角色用 `status`，菜单/配置删除仅通过 Flyway 迁移执行。
- 资源与系统参数不提供运行时创建/删除接口；新增/删除由 Flyway 迁移维护，后台只更新展示属性或参数值。
- 系统参数通过 `ConfigProvider` 读取，使用 Redis 缓存，TTL 30 分钟；更新后立即删除缓存。
- 具体表结构见 `03-数据库设计.md`，并遵守 `../rules/database-rules.md`。

## 6. API 与契约

- 路径带版本：`/api/v1/admin/**`、`/api/v1/public/**`。
- 响应体：`{ code, message, data }`；错误使用 4xx/5xx，错误码字符串 + 模块前缀。
- 请求 ID：`X-Request-Id` 请求/响应头，不进 body。
- 分页：`page` 从 1 开始，`size` 默认 20 / 上限 100；返回 `items`、`total`、`page`、`size`。
- 校验错误放 `data.fieldErrors`。
- OpenAPI 由 SpringDoc 生成，前端生成 TypeScript 类型。
- 具体端点与 DTO 见 `04-API接口设计.md`，并遵守 `../rules/api-rules.md`。

## 7. 前端架构

### 7.1 工程目录

前端与后端当前同处一个仓库，分别位于 `frontend/admin/` 与 `frontend/portal/`；各工程保持独立依赖、独立构建与部署，后续可拆分为独立仓库。

| 目录 | 职责 |
|---|---|
| `frontend/admin/` | 管理端，认证、RBAC、系统参数、日志 |
| `frontend/portal/` | 门户，匿名公开 API 与骨架 |

API 类型由后端 OpenAPI 生成，各自提交 `openapi.json` 快照并在 CI 校验。

### 7.2 Admin

- Vue 3 + TypeScript + Vite + shadcn-vue。
- Pinia 保存用户、权限码、菜单；Vue Router 静态路由 + `meta.permission`。
- `v-permission` 控制按钮；侧边栏由后端菜单驱动。
- Axios 薄封装处理 CSRF、401/403、错误归一化。
- 启动调用 `/api/v1/admin/auth/me` 恢复登录态。
- 组件：`components/ui` 为 shadcn-vue 生成，`components/app` 放 DataTable、PermissionTree 等封装。
- 测试：Playwright 覆盖登录、401/403、用户 CRUD、角色授权。

### 7.3 Portal

- Vue 3 + TypeScript + Vite + Tailwind + shadcn-vue，与 Admin 保持同一设计语言。
- 匿名客户端，不挂认证拦截器。
- 初期仅公开只读 API 与工程骨架。

## 8. 部署与运行

- 同一域名：`/admin`、`/portal`、`/api/v1`，Nginx 反向代理。
- 同源部署，无 CORS；Cookie 正常工作。
- 后端单应用部署；Redis 与 MySQL 为外部依赖。
- Actuator 仅暴露 `/actuator/health`，用于容器与负载均衡健康检查。
- 配置通过环境变量与 profile 注入；敏感信息不入库、不入日志。
- Docker 镜像与 Compose 见 `05-实施计划与工程规范.md`。

## 9. 关键决策记录

| ID | 决策 | 替代方案 | 主要理由 | 代价 |
|---|---|---|---|---|
| ADR-001 | 单体多模块 + ArchUnit | Spring Modulith、微服务 | 边界清晰、零运行时开销、易维护 | 规则需自行维护 |
| ADR-002 | Spring Security + opaque token | JWT、Spring Session、Sa-Token | 可即时吊销、保留 CSRF 与方法级鉴权 | 需自建 token 过滤器 |
| ADR-003 | 统一资源树 | 菜单/权限分离 | 一张树、一条授权关系，贴合共用权限码 | UI 元数据与授权同表 |
| ADR-004 | 不预埋 `tenant_id` | 预埋字段 | 当前单租户，保持表结构干净 | 未来多租户需全表迁移 |
| ADR-005 | 不做全局逻辑删除 | `@TableLogic`、`deleted_at` | 避免唯一索引与查询污染 | 删除不可恢复 |
| ADR-006 | MyBatis-Plus | 原生 MyBatis、JPA | CRUD 样板少、分页与填充方便 | 需约束使用边界 |
| ADR-007 | shadcn-vue | Element Plus、Naive UI、Ant Design Vue | 设计与代码完全可控、Tailwind 体系 | 复杂后台组件需自建 |
| ADR-008 | 仅 Playwright | Vitest + Playwright、仅 Vitest | 关键流程真实浏览器覆盖 | 反馈慢、无组件级测试 |
| ADR-009 | 本地时区 Asia/Shanghai | UTC | 单时区部署，前后端直观 | 多地域迁移成本高 |
| ADR-010 | 自增 BIGINT 主键 | 雪花 ID、UUID/ULID | 简单、索引友好、无 JS 精度问题 | ID 可枚举 |
| ADR-011 | Flyway 预置核心资源 | 启动 upsert、首次初始化 | 版本化、可评审、可追溯 | 新增页面需迁移 |
| ADR-012 | Walking skeleton + 边实现边验证 | 先做独立 spike | 尽早验证端到端契约 | 兼容性问题在 Phase 1 暴露 |

## 10. 风险与回退

| 风险 | 影响 | 应对 / 回退 |
|---|---|---|
| Boot 4 生态兼容性 | 依赖不可用 | Phase 1A 验证；MP 失败切原生 MyBatis，SpringDoc 降级 |
| Tailwind v4 / shadcn-vue 工具链 | 前端构建失败 | Phase 1A 验证；回退 Element Plus + SCSS |
| 静态路由与菜单漂移 | 菜单指向 404 | 前端启动校验；发版与迁移成对执行 |
| 仅 Playwright | 回归反馈慢 | 控制 E2E 范围；核心组件频繁改动时补 Vitest |
| shadcn-vue 源码复制 | 升级需人工维护 | 记录版本；定制集中在 `components/app` |
| 本地时区 | 多地域迁移成本高 | 统一三处时区配置；文档明确假设 |
| 自增 ID 可枚举 | 公开接口暴露数据量 | 管理端接受；公开 API 用外部标识 |
| 多实例日志清理 | 重复执行 | 引入 ShedLock 或等价分布式锁 |

## 11. 实施门与验收

1. Boot 4.1.x + Java 25 启动。
