# API 接口设计规范

> 适用范围：`docs/design/04-API接口设计.md`、所有 Controller、OpenAPI 定义、前端客户端
> 状态：v0.3（评审修订）
> 更新：2026-11-12
> 关联：`docs/design/02-技术选型与整体架构.md`、`docs/design/04-API接口设计.md`

## 1. 目的与基本原则

本规范用于统一 HTTP API 的设计、实现和维护，确保接口一致、易理解、安全且便于测试。默认以 REST 风格 HTTP API 为参考；如采用其他风格，应在项目设计文档中说明。

## 2. 路径与 HTTP 方法

1. 路径应清晰、稳定，默认使用小写英文和项目统一的命名风格。
2. 资源路径通常使用名词表达，例如 `/users`，避免含糊名称和无必要的动词。
3. HTTP 方法应表达明确语义：
   - `GET`：读取资源，不应产生业务副作用。
   - `POST`：创建资源或执行非幂等操作。
   - `PUT`：整体替换资源，需明确语义。
   - `PATCH`：部分更新资源。
   - `DELETE`：删除资源。
4. 路径参数用于标识资源；查询参数用于筛选、排序和分页；请求体用于提交创建或更新数据。
5. 不得将密码、令牌等敏感信息放入 URL 查询参数。

## 3. 请求参数与校验

1. 每个接口应明确参数名称、类型、是否必填、默认值、格式和校验规则。
2. 服务端必须校验所有客户端输入，不能只依赖前端校验。
3. 对字符串长度、数值范围、枚举值、日期格式和数组大小设置合理限制。

## 4. 统一响应格式

1. 项目必须统一成功和失败响应结构，并在 API 设计文档中确认最终格式。
2. 同类接口应使用一致的字段命名和数据类型。
3. 响应只应包含调用方需要的数据，不应默认暴露数据库内部字段或敏感信息。
4. 列表接口应统一分页结构，并明确页码起始值、默认页大小。
5. HTTP 状态码与业务成功标记不得互相矛盾；不得将所有错误都返回为 HTTP 200。

## 5. HTTP 状态码与业务错误码

1. 使用合适的 HTTP 状态码表达成功、创建成功、参数错误、未认证、无权限、资源不存在、冲突和服务端错误等结果。
2. 业务错误码应稳定、可识别，并统一命名或编号规则。
3. 错误响应应提供足够的处理信息，但不得泄露内部实现细节。
4. 参数校验错误应尽可能指出相关字段及原因。
5. 不应仅凭 HTTP 200 判断业务操作成功。

## 6. 本项目落地约定

以下约定是对上述规范的补充，均不得与其冲突。

### 6.1 路径与版本

- 所有路径带版本：`/api/v1/admin/**`、`/api/v1/public/**`。
- 路径小写；多词段使用 kebab-case，如 `login-logs`。
- 资源名使用复数；单例资源（如站点配置）可使用单数，但必须在 API 文档中说明。
- 禁止文件扩展名与尾斜杠。
- 资源路径按模块分段：`iam`、`system`、`audit`。
- 动作使用子资源：`/status`、`/roles`、`/reset-password`。
- 用户不提供 `DELETE`，使用 `PATCH .../status` 禁用。
- 破坏性变更使用 `/api/v2`；v1 只允许加法式演进。

### 6.2 响应结构

- 响应体固定为 `{ code, message, data }`；`data` 内部默认忽略 `null` 字段。
- 成功时 `code = "OK"`，`message = "success"`，`data` 为业务数据。
- 错误时使用对应 HTTP 状态；`data` 可携带错误明细，如 `fieldErrors`。
- 请求 ID 走 `X-Request-Id` 请求 / 响应头，禁止放进响应体。
- 成功状态：`200` 普通请求，`201` 创建并返回响应体，`204` 删除或动作执行成功且无响应体。
- 更新请求使用显式 DTO 表达“未提供/清空”，规则见 6.5。
- JSON 字段使用 camelCase；时间使用 `yyyy-MM-dd'T'HH:mm:ss.SSS` 本地时间，不带偏移量。
- 自增 ID 以 JSON number 返回；布尔字段使用 JSON boolean。
- 前端必须同时检查 HTTP 状态与 `code`，不得只看 HTTP 200。

### 6.3 错误码

- 错误码使用大写 snake_case + 模块前缀，如 `IAM_USER_NOT_FOUND`。
- 每个错误码绑定一个 HTTP 状态。
- 错误码一经发布不得复用或改变语义。
- 错误码按模块注册：`Common`、`Auth`、`Iam`、`Sys`、`Audit`。
- 新增错误码必须同步更新 `04-API接口设计.md`。
- 禁止在响应中返回堆栈、SQL、内部类名等实现细节。
- 登录失败统一提示“用户名或密码错误”，避免账号枚举。

### 6.4 分页、排序与筛选

- 分页参数 `page` 从 1 开始，`size` 默认 20、上限 100。
- 排序参数 `sort=field,asc|desc`，字段必须在白名单内。
- 分页响应：`items`、`total`、`page`、`size`。
- 禁止无界列表查询。
- 筛选条件使用显式查询参数；禁止通用查询语言或任意字段拼接。
- 游标分页仅用于后续公开信息流，不作为管理端默认方案。

### 6.5 DTO 与参数校验

- 请求 / 响应必须使用显式 DTO；禁止暴露 PO 或领域实体。
- DTO / VO 使用 record；使用 Jakarta Bean Validation 校验。
- 字段校验错误放入 `data.fieldErrors`，格式 `{ field, message }`。
- Controller 只做接收、校验、调用应用服务、返回 VO；禁止业务逻辑。
- 禁止用 `Map` 或任意 JSON 承载业务请求体。
- 枚举字段使用字符串编码，并在服务端校验白名单。
- 应忽略未知字段以保持向后兼容；禁止依赖未知字段承载业务含义。
- 请求体大小、字符串长度、分页大小必须有上限。
- 更新语义必须明确：`PUT` 全量替换，`PATCH` 只更新显式字段。
- `PUT` 全量替换时，请求体必须包含全部可更新字段；可空字段使用显式 `null` 表示清空，缺失字段按校验失败处理。
- `PATCH` 只更新请求体中显式提供的字段。
- 禁止用 `null` 同时表达“未提供”和“清空”；需要清空时使用显式字段或专用接口。

### 6.6 认证与授权

- Web 使用 `HttpOnly` Cookie；App / 小程序使用 `Authorization: Bearer`。
- Cookie 模式必须启用 CSRF；Bearer 模式跳过。
- 接口鉴权统一使用 `@PreAuthorize("@perm.has('...')")`。
- 权限码格式 `module:resource:action`，如 `iam:user:create`。
- `401` 时前端清理登录态并跳转；`403` 只提示无权限，不退出登录。
- 认证端点固定为 `/api/v1/admin/auth/login`、`logout`、`me`、`csrf`、`change-password`。
- 强制下线后，目标 token 必须在下一个请求立即失效。
- 错误响应不得泄露用户是否存在、权限细节或 token 信息。
- 登录接口必须有失败计数与锁定；公开写接口必须有速率限制。

### 6.7 OpenAPI 与契约

- 使用 SpringDoc 生成 OpenAPI；按 `admin` / `public` 分组。
- 必须定义泛型 `ApiResponse<T>` 与统一错误 schema。
- 每个端点必须有摘要、参数、响应与至少一个示例。
- 安全方案声明 `cookieAuth` 与 `bearerAuth`。
- 前端从 OpenAPI 生成 TypeScript 类型；提交 `openapi.json` 快照，CI 校验生成物一致。
- 废弃接口必须标注废弃原因、替代端点与移除版本。
- 禁止存在未写入 OpenAPI 的业务端点。

### 6.8 安全

- 禁止在响应或日志中输出密码、token、Cookie、密钥。
- 认证错误使用统一模糊提示，避免账号枚举。
- 禁止向客户端返回堆栈或框架异常原文。
- 必须校验 `Content-Type` 与请求体大小；文件上传另定规则。
- 默认不做 CORS；确需跨域时使用显式白名单，禁止 `*` + 凭证。
- Cookie 模式写请求必须携带 `X-XSRF-TOKEN`。
- 禁止在查询参数中传递 token、密码、密钥。
- 公开写接口上线前必须完成 CSRF 与限流设计。

### 6.9 幂等与并发

- `POST` 默认非幂等；依赖唯一约束或乐观锁防止重复。
- 单资源更新携带 `version`，冲突返回 `409 COMMON_OPTIMISTIC_LOCK`。
- 关联集合的幂等全量替换可不使用 `version`，但必须在 API 文档中说明并发覆盖策略。
- v1 不实现通用 `Idempotency-Key`；高风险接口后续按需增加。

## 7. 评审清单

- [ ] 路径带 `/api/v1`，资源名复数、kebab-case。
- [ ] HTTP 方法与状态码符合语义。
- [ ] 响应为 `{ code, message, data }`；无 `traceId` 字段。
- [ ] 错误码已注册、绑定 HTTP 状态、未复用。
- [ ] 请求 / 响应为显式 DTO，校验完整。
- [ ] PUT 全量替换、PATCH 显式字段、null 清空语义明确。
- [ ] 关联集合全量替换已说明是否使用 version。
- [ ] 分页、排序、筛选有上限与白名单。
- [ ] 鉴权注解与权限码正确。
- [ ] 敏感信息未进入响应或日志。
- [ ] OpenAPI 有摘要、示例与安全方案。
- [ ] 前端类型已从最新快照生成。

## 8. 示例

### 登录成功

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "user": { "id": 1, "username": "admin", "nickname": "超级管理员" },
    "superAdmin": true,
    "permissions": [],
    "menus": [],
    "mustChangePassword": false
  }
}
```

### 分页查询

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "items": [],
    "total": 0,
    "page": 1,
    "size": 20
  }
}
```

### 校验错误

```json
{
  "code": "COMMON_VALIDATION_FAILED",
  "message": "参数校验失败",
  "data": {
    "fieldErrors": [
      { "field": "username", "message": "不能为空" }
    ]
  }
}
```
