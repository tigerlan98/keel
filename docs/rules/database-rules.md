# 数据库设计规范

> 适用范围：`docs/design/03-数据库设计.md`、所有表结构与迁移评审
> 状态：v0.3（评审修订）
> 更新：2026-11-12
> 关联：`docs/design/02-技术选型与整体架构.md`

## 1. 目的与基本原则

本规范用于指导数据库概念、逻辑和物理设计，保证数据模型一致、完整、安全且易维护。

## 2. 命名规范

- 数据库对象默认使用小写英文和下划线分隔的 snake_case。
- 表名、字段名应表达明确业务含义，避免拼音、无意义缩写和含糊名称。
- 表名单复数风格应在项目中统一。
- 主键默认命名为 `id`；外键采用关联实体名加 `_id`，例如 `user_id`。
- 时间字段应明确表达含义，例如 `created_at`、`updated_at`。
- 避免使用数据库保留字作为对象名称。
- 命名规则一经确认，应在新增表和字段中保持一致。

## 3. 表与字段设计

- 字段类型应准确表达数据含义，避免所有字段统一使用字符串或过大的类型。
- 必填字段应设置 `NOT NULL`；仅在业务允许缺失时使用可空字段。
- 默认值必须有明确业务含义，不得掩盖数据缺失或无效状态。
- 金额等需要精确计算的数据应使用适合的定点数类型，避免浮点数误差。
- 日期时间字段应统一时区策略；推荐 UTC 存储并在展示层转换，若采用其他策略须明确记录。
- 状态字段应具有明确、有限且有文档说明的取值集合。
- 不得将多个独立业务值拼接到一个字段，除非该字段确实表示不可拆分内容或采用明确约定的结构化存储。

## 4. 主键、外键与完整性约束

- 表必须设计主键，主键生成策略应在项目中统一使用自增主键；主键必须唯一、非空，并稳定标识一条记录。
- 禁止使用物理外键，不得通过 SQL、ORM 模型或数据库迁移创建 `FOREIGN KEY` 约束。表之间通过逻辑关联字段建立关系，由应用层负责关联校验和业务完整性维护。
- 业务上必须唯一的值应使用唯一约束，而不应只依赖应用代码检查。
- 数据完整性不能只依赖前端校验；服务端应校验输入，数据库约束应作为重要防线。

## 5. 本项目落地约定

以下约定是对上述规范的补充，均不得与其冲突。

### 5.1 基础

- 使用 MySQL 8.x、InnoDB、`utf8mb4` / `utf8mb4_0900_ai_ci`。
- 单库单 schema；禁止跨库 JOIN。
- 所有表和字段必须有中文注释；表注释说明模块与用途。

### 5.2 命名

- 表名使用单数，模块前缀：`iam_`、`sys_`、`aud_`。
- 主键统一 `id`；逻辑关联列 `{实体}_id`。
- 唯一索引 `uk_{table}_{columns}`；普通索引 `idx_{table}_{columns}`。
- 时间列以 `_at` 结尾；枚举列优先使用 `_type` / `_status` / `_code` 后缀。
- 布尔列使用 `TINYINT(1)`，命名表达语义，不使用 `is_` 前缀。

### 5.3 类型

- 主键、逻辑关联列使用 `BIGINT`，主键 `AUTO_INCREMENT`。
- 时间使用 `DATETIME(3)`；禁止 `TIMESTAMP`。
- 枚举存 `VARCHAR(32)` 编码，禁止数据库 `ENUM`。
- 布尔 `TINYINT(1) NOT NULL DEFAULT 0`。
- 金额 `DECIMAL(18,2)`；禁止 `FLOAT` / `DOUBLE`。
- 字符串使用 `VARCHAR(n)`；`TEXT` 仅用于大文本。
- 常用长度：IP `VARCHAR(64)`、User-Agent `VARCHAR(512)`、URI `VARCHAR(512)`、`trace_id` `VARCHAR(64)`、密码哈希 `VARCHAR(100)`。

### 5.4 时区（明确记录的例外）

规范推荐 UTC 存储。本项目为单时区部署，统一采用 `Asia/Shanghai` 本地时间，并满足：

- JVM、MySQL 会话、JDBC 连接三处时区一致。
- Java 使用 `LocalDateTime`，API 输出不带偏移量的本地时间。
- 该选择已在 `02-技术选型与整体架构.md` 记录；未来多地域部署需迁移到 UTC。

### 5.5 完整性

- 禁止物理外键；关联关系由应用服务校验。
- 业务唯一值使用唯一约束。
- 关联表使用唯一组合索引，并对关联列建立查询索引。
- 日志表不建物理外键，用户 ID 等按值存储。

### 5.6 审计与状态

- 可变业务表必须有 `created_at`、`created_by`、`updated_at`、`updated_by`。
- 追加型日志表只需 `created_at`。
- `version INT NOT NULL DEFAULT 0` 仅用于用户、角色、资源、系统参数。
- 禁止全局逻辑删除；用户/角色用 `status` 控制，菜单/配置硬删除。
- 状态值统一 `ENABLED` / `DISABLED`；登录锁定由 Redis 计数控制，不入库。
- 审计字段由 `MetaObjectHandler` 填充。

### 5.7 索引与迁移

- 索引按查询设计，遵循“等值 → 范围 → 排序”；上线前用 `EXPLAIN` 验证核心查询。
- 禁止重复、冗余、单独低基数列索引。
- 列表查询必须分页。
- 所有结构变更通过 Flyway；只前进，不修改已执行脚本。
- `scripts/sql/schema.sql` 是结构与索引的参考基线，必须与 `docs/design/03-数据库设计.md` 保持一致；实际执行以 Flyway 为准。
- 版本段：`0001–0999` 基础 / 预留，`1000–1999` `iam`，`2000–2999` `system`，`3000–3999` `audit`，`9000–9999` 跨模块种子（`bootstrap`）。
- 模块迁移只操作本模块表；跨模块种子统一放 `bootstrap`。
- 种子数据按业务 `code` 幂等写入，禁止依赖固定自增 ID。
- `SUPER_ADMIN` 角色与核心资源由全局种子写入；初始管理员由启动器创建。

## 6. 评审清单

- [ ] 命名符合 snake_case、单数表名、模块前缀。
- [ ] 表和字段有注释。
- [ ] 必填字段 `NOT NULL`，默认值有意义。
- [ ] 类型准确；时间 `DATETIME(3)`；金额 `DECIMAL`；枚举字符串编码。
- [ ] 主键自增、唯一、非空。
- [ ] 无物理外键；逻辑关联列有索引。
- [ ] 业务唯一值有唯一约束。
- [ ] 状态取值集合有文档说明。
- [ ] 审计字段齐全；日志表无 `updated_*`。
- [ ] 无逻辑删除列。
- [ ] 无多值拼接字段。
- [ ] 时区策略明确且三处一致。
- [ ] 迁移版本段、文件命名、幂等种子符合约定。
- [ ] `scripts/sql/schema.sql` 与设计文档一致。
- [ ] 核心查询有索引并通过 `EXPLAIN`。

任何偏离必须在 `docs/design/02-技术选型与整体架构.md` 的 ADR 中记录理由、影响与回退方案，并同步更新本文档。
